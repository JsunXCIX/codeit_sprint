# 내가 Git을 처음 배울 때 제일 막혔던 개념 정리

Git을 처음 배울 때 가장 혼란스러웠던 순간은 "과거로 돌아가는 것"과 "갈라진 작업(Branch)을 하나로 합치는 것"이었습니다.  
이 개념들을 어떻게 이해하면 쉬운지 직관적으로 정리해 봅니다.

## 1. 과거로 가는 방법
### `git reset` : 시간을 완전히 되감기
- 한 줄 요약: 영화 시간을 뒤로 되돌리듯, 특정 시점 이후의 모든 미래 기록을 지우고 돌아감.
- 쉬운 이해: "아, 이번 커밋 망했다. 그냥 이 커밋 없던 셈 치고 이전으로 돌아갈래!"
- 주의점: 이미 원격 저장소(GitHub)에 올린 커밋이라면 다른 사람의 작업과 충돌이 발생할 수 있으므로, 혼자 작업하는 Local 상태에서 주로 사용함.



### `git revert` : 잘못된 과거 청산하기 (새로운 커밋으로 취소)
- 한 줄 요약: 잘못된 과거를 지우는 것이 아니라, "이전 커밋을 취소함"이라는 새로운 기록을 추가함.
- 쉬운 이해: 실수로 작성한 글을 삭제하는 게 아니라, "방금 한 말 취소합니다"라는 글을 새로 덧붙이는 방식임.
- 특징: 기존의 커밋 이력(History)이 그대로 유지되므로, 협업 공간에서 안전하게 과거의 실수를 바로잡을 때 사용함.



### `git checkout` : 과거 잠깐 방문하기
- 한 줄 요약: 기록을 지우거나 바꾸지 않고, 과거의 특정 시점으로 눈만 이동해서 둘러봄.
- 쉬운 이해: 박물관에서 과거 유물을 둘러보듯 "그때 코드 상태가 어땠지?" 하고 타임머신을 타고 잠시 구경하러 가는 것임.
- 특징: 현재 작업 상태에 영향을 주지 않고 안전하게 과거 코드를 확인 및 테스트해 볼 수 있음.

<br>

## 2. 브랜치 합치는 방법
### `git merge` : 두 역사를 하나로 이어 붙이기
- 한 줄 요약: 두 브랜치에서의 변경 사항을 합쳐 새로운 '합병 커밋(Merge Commit)'을 만듬.
- 쉬운 이해: "각자 만든 코드를 모아서 합침"이라는 기록(이정표)을 남기며 두 줄기를 연결하는 방식임.
- 장점: 작업이 언제, 어떻게 나누어지고 합쳐졌는지 실제 히스토리가 있는 그대로 보존됨.



### `git rebase` : 뿌리를 옮겨 일렬로 깔끔하게 정돈하기
- 한 줄 요약: 내 브랜치의 베이스(뿌리)를 다른 브랜치의 최신 커밋 뒤로 옮겨, 마치 한 줄로 작업한 것처럼 히스토리를 재작성함.
- 쉬운 이해: "내가 한 작업을 메인 줄기의 가장 최신 작업 뒤로 붙여서 줄을 똑바로 세우자!"
- 장점: 복잡한 브랜치 줄기 없이 커밋 히스토리가 깔끔하게 단일 선형으로 정리됨.

<br>

## 요약
- 과거로 갈 때 : 기록을 지우려면 `reset`, 안전하게 취소 기록을 남기려면 `revert`, 둘러보기만 하려면 `checkout`
- 브랜치를 합칠 때 : 복잡해도 사실적인 기록을 남기려면 `merge`, 일렬로 깔끔한 기록을 만들려면 `rebase`

<br>

## 위 개념 중, 내가 생각한 중요 팁
### 'HEAD'의 위치를 아는 것!
- Git으로 과거로 가거나 브랜치를 합칠 때 가장 중요한 것은 "지금 내 `HEAD`(현재 작업 위치)가 어디를 가리키고 있는가?"를 정확히 파악하는 것이었습니다. 
`reset`이나 `checkout`을 할 때도 내 `HEAD`를 어디로 이동시킬지 알아야 하고, 
`merge`와 `rebase`를 할 때도 어느 브랜치에 `HEAD`를 두고 명령어 대상(target)을 지정하느냐에 따라 기준과 결과가 완전히 달라지기 때문입니다. 
처음에는 단순히 명령어 옵션을 외우느라 바빴지만, `HEAD`라는 '현재 내 위치'를 중심으로 생각하기 시작하면서 비로소 Git의 흐름이 명확하게 눈에 보이기 시작했습니다.
